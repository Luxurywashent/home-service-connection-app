# Expo Go Launch Incident Investigation

**Application:** Home Service Connection  
**Incident:** Expo Go displayed “There was a problem running the requested app” with an HTTP 500 HTML response.  
**Investigation status:** Root causes identified; launch chain repaired and revalidated.  
**Scope:** Development/Expo Go launch only. This report does not claim that customer-data, booking, or server-worker flows are fully validated.

## Executive Summary

The failure occurred **before the React Native application could load**. The evidence shows that Expo Go was receiving an HTML error document generated by the development sandbox/proxy instead of the Expo-native manifest or JavaScript bundle it requires. This was a development-launch delivery problem, not a Stripe payment failure and not an in-app sign-in failure.

The issue had several contributing causes. The copied project had previously started Expo in web-only mode, which returns an HTML document rather than the `application/expo+json` manifest Expo Go expects. The development command also forced a cold Metro cache on every restart, causing the initial iOS bundle to take roughly one minute to compile. In addition, the `npx expo` process produced non-interactive command errors, and unrelated API background workers were consuming resources while reporting missing database tables and columns.

The current startup path now starts **native Metro only**, avoids `npx`, does not clear the cache on every restart, and warms the iOS bundle before a device requests it. The public manifest, all declared icon assets, and the current public iOS bundle were individually tested successfully.

## Evidence and Findings

### 1. The reported screen was a proxy-generated HTML response

The supplied screenshot shows Expo Go reporting an HTTP 500 and then rendering an HTML document titled **“Manus Sandbox.”** Expo Go expects an Expo manifest and later a JavaScript bundle; it cannot launch an app from this HTML error document. This places the initial failure in the delivery path between Expo Go and the sandbox, prior to application execution.

### 2. Expo was initially running in web-only mode

The old development command used `expo start --web`. When queried as Expo Go, that endpoint returned `text/html` containing the web preview document. A native Expo client requires a manifest with `content-type: application/expo+json`; receiving HTML can yield the kind of launch failure displayed in the screenshot.

**Repair:** The command now runs native Expo without the `--web` flag.

### 3. Forced cache clears made every first iOS load unusually slow

The prior command also used `--clear`, which discarded Metro’s transform cache on every restart. Recorded initial iOS bundle timings were approximately **70 seconds** and **59 seconds** for a 2,346-module bundle. During sandbox resets or a slow proxy connection, that cold start can cause the device request to arrive while the endpoint is not ready.

**Repair:** The startup command no longer clears Metro’s cache on each restart. A lightweight warm-up request compiles and drains the iOS bundle immediately after Metro starts, without retaining the large bundle in memory.

### 4. `npx expo` produced non-interactive command errors

The server log recorded:

> `CommandError: Input is required, but 'npx expo' is in non-interactive mode.`

This made the development process less reliable. The launch command now invokes the project-local Expo CLI directly through a startup script rather than using `npx`.

### 5. API background workers were unrelated but destabilizing

When the API server ran alongside Metro, background jobs repeatedly queried missing database structures such as `email_queue`, `sales_callbacks.source_callback`, and `schedule_jobs.payment_paid_at`. These errors do **not** explain the initial Expo manifest type mismatch, but they added CPU, database, and log load during a mobile launch.

**Repair:** The default `dev` command is now Expo/Metro only. The API server remains intentionally available through `pnpm dev:full` when backend work is needed.

### 6. Sandbox URLs are session-specific and can become stale

During diagnosis, a prior public host returned a proxy connection failure after a sandbox reset. Expo Go QR links point to session-specific launch hosts. A QR code or `exps://` address from before a server reset can therefore fail even if the current server is healthy.

**Required user action:** Use the **current QR code in the project panel** after the current server is running. Do not reuse a previously saved QR image or older `exps://` link.

## Changes Applied

| Change | Purpose |
|---|---|
| Replaced `expo start --web` with native Expo startup | Returns an Expo manifest to Expo Go instead of a web document. |
| Removed unconditional `--clear` | Preserves Metro cache and avoids long cold builds on every restart. |
| Added `scripts/start-metro.mjs` | Runs the local Expo CLI directly and pre-warms the iOS bundle. |
| Kept `scripts/prepare-metro-assets.mjs` | Ensures required icon/font aliases exist for Metro asset delivery. |
| Changed default `dev` to Metro-only | Avoids unrelated database worker load while testing Expo Go. |
| Preserved `dev:full` | Allows the API server to be started deliberately for backend work. |

## How to Launch Now

1. Open the project’s **Preview** panel and scan the **current** QR code with Expo Go. Do not use a saved image or an older link.
2. Keep Expo Go open through the first launch. The iOS bundle has already been warmed, so it should not need the prior cold-build wait.
3. If Expo Go still shows an error, capture the **entire launch URL** shown in the Expo Go history/details screen and send it. That identifies whether the device is still using a stale session host versus the current endpoint.

## Remaining Work Outside This Incident

The new empty database does not yet match all copied background-worker expectations. Before turning on `pnpm dev:full` for operational testing, the missing tables and columns should be reconciled or the associated monitors should be made conditional. Separately, the emailed estimate link still needs its own public destination route; it is unrelated to the Expo Go startup failure.
